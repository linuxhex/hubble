## 性能问题（非功能性问题）

### 问题描述
两个页面的数据查询性能存在严重问题：

**接口劣化页面**：
- 当前时段查询：121秒
- 上期时段查询：116-160秒
- 总耗时：237-281秒（4-5分钟）
- 过滤统计：total=350-353, 无数据=214-226, 无上期调用=4-28, RT未增加=68-86, 最终结果=37-40

**流量暴涨页面**：
- 总接口：289
- 涨幅>0的：44
- 返回：30
- 查询耗时：与接口劣化类似（约4-5分钟）

### 影响
1. **首次访问体验差**：首次请求触发异步加载，返回空数据，用户看到"暂无数据"
2. **需要等待或刷新**：用户需要等待4-5分钟或手动刷新页面才能看到数据
3. **缓存机制**：数据加载完成后会缓存，后续访问正常

### 根因分析
1. **queryApiStats 方法性能差**：
   - 每次查询需要调用 ARMS SearchTraces + SLS 分页采样
   - ARMS listApps 返回 203 个应用
   - SLS 分页采样 50 页共 5000 条日志
   - 单个时段查询耗时 120+ 秒

2. **异步加载模式**：
   - 首次请求触发后台异步加载
   - 立即返回空列表
   - 用户需要等待或刷新

### 建议优化方案
1. **预加载缓存**：应用启动时或定时任务预加载数据，避免用户首次访问等待
2. **优化查询性能**：
   - 减少 SLS 分页数量（当前 50 页太多）
   - 使用批量查询替代逐个服务查询
   - 考虑使用更高效的聚合查询
3. **改进用户体验**：
   - 显示加载进度或预计等待时间
   - 提供"数据加载中，请稍候..."的提示
   - 考虑使用 WebSocket 推送加载完成通知
4. **缩短查询时间范围**：
   - 当前 day 模式查询 15 分钟数据
   - 考虑改为查询 5 分钟或更短时间范围
   - 或者使用更粗粒度的聚合数据
